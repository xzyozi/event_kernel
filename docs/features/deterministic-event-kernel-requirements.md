# Deterministic Event Kernel システム要件定義書

**Deterministic Event Kernel（決定論的リプレイ・イベント駆動カーネル）** の要件を定義する。時系列データのバックテストや複雑な状態機械シミュレーションで、実行速度の確保と「先読みバイアス（未来データの参照）」の構造的排除を両立させることを目的とする。

## 1. システム概要と目的

### 1.1 背景と解決する課題

Python単体で時系列シミュレーションやバックテストを実装する場合、次の3点が技術的負債および検証精度のボトルネックとなる。

1. **先読みバイアス（Look-ahead Bias）の混入:** DataFrame全体の操作やインデックス指定のミスにより、評価時点より未来のレコードや集計値にコードがアクセスしてしまう。
2. **非決定性（Non-determinism）:** 並列処理の競合、未初期化メモリ、システム時刻への依存、順序不定なハッシュマップの走査などにより、同一条件で再実行しても結果が一致しない。
3. **スループットの限界:** ティック単位・秒単位の高頻度イベント（数百万〜数億件）をPythonのオブジェクトループで処理すると、パラメータ探索や検証サイクルが著しく遅延する。

### 1.2 システムの目的とスコープ

**目的:** コアとなるイベント駆動状態機械を **Rust** で実装し（判断理由は ADR-002）、時間軸の単調増加とメモリ境界を型・インターフェースレベルで強制する決定論的リプレイ基盤を構築する。

**インスコープ:**

- 単調増加タイムスタンプに基づくイベントスケジューリングと配送制御
- 未来データへのアクセスを遮断する読み取り専用コンテキストの提供
- 任意時点での完全な状態スナップショット保存・復元（チェックポイント機能）
- 外部ホスト言語（Python）からの戦略ロジック注入および結果抽出用FFI境界

**アウトオブスコープ:**

- 本番環境へのリアルタイム発注・ネットワーク通信機能（ただし、将来的な本番アダプタ接続を見据えたポート契約の互換性は維持する）
- 戦略ロジック自体のアルゴリズム設計や機械学習モデルの学習処理

## 2. アーキテクチャ方針・境界設計

本システムは **ヘキサゴナルアーキテクチャ（Port & Adapter）** を採用し、コアカーネルを外部I/Oおよびホスト言語のランタイムから完全に隔離する。

```text
+-------------------------------------------------------------------+
| Host Layer (Python: Orchestration, Parameter Sweep, Analytics)    |
+-------------------------------------------------------------------+
                                  |  C ABI / Zero-Copy FFI Boundary
+-------------------------------------------------------------------+
| Core Kernel (Rust: Zero-Allocation State Machine)                 |
|  - Monotonic Event Loop   - Ring Buffer   - Deterministic PRNG    |
+-------------------------------------------------------------------+
       |                  |                  |                 |
 [ClockPort]      [EventFeedPort]    [ExecutionPort]   [SnapshotPort]
       |                  |                  |                 |
+-------------------------------------------------------------------+
| Adapter Layer (Parquet/CSV Reader, Simulated Broker, Memory/Disk) |
+-------------------------------------------------------------------+
```

### 2.1 設計原則

- **時間の単一方向性（Strict Causality）:** カーネル内部の現在時刻は `ClockPort` が進めるイベントタイムスタンプのみによって更新される。過去の時刻への巻き戻し（スナップショット復元時を除く）と未来時刻の参照を禁止する。
- **ホットパスでの動的メモリ確保禁止:** イベントループ実行中はヒープアロケーションを行わない。初期化時に確保した固定長リングバッファおよび構造体配列（SoA: Structure of Arrays）上で状態を遷移させる。
- **C ABI による言語境界の固定:** コアとPython間のデータ受け渡しはC互換の構造体ポインタまたは共有メモリバッファ経由で行い、FFIコール回数を最小化する。

### 2.2 横断方針

#### 並行性モデル

- 1カーネルインスタンスは完全にシングルスレッドで実行する。カーネル内部にロック（`Mutex` など）、アトミック操作、ワーカースレッドを持たない。
- カーネルの型はスレッド間の移動（`Send`）を許可し、複数スレッドからの同時アクセス（`Sync`）を型レベルで禁止する（`!Sync`）。
- 並列化はインスタンス間で行う（Share-Nothing）。パラメータ探索では、読み取り専用の入力データを不変共有（`Arc` など、カーネルの外側）し、スレッドごとに独立したカーネルインスタンス（State Arena、キュー、PRNG）を生成する。
- Pythonコールバックを持つインスタンスは、GIL のため実質的に直列で動く。インスタンス並列によるスループット向上は、ネイティブ戦略を対象とする。

#### 致命的エラーと `Poisoned` 状態

- 因果律違反（FR-01-2）とパニックの捕捉（ADR-003 5.1-4）は、カーネルのハンドルを `Poisoned` 状態に遷移させる。
- `Poisoned` のハンドルは、`step`、`snapshot`、`submit_action` を拒否する。`restore` の可否は DD で決める（ADR-003 5.1-9）。
- 遅延したイベントを破棄して続行したい場合は、カーネルの外側のアダプタ層（`EventFeedPort` のラッパー）で事前にフィルタリングし、監査ログを出力してからカーネルへ供給する。

#### 固定容量の溢れ時の動作

論理時間を止める待機（バックプレッシャー）は、決定論的なイベントループと相性が悪いため採用しない。バッファの役割ごとに動作を分ける。

| 対象                            | 溢れ時の動作                                                        | 補足                                                                                                       |
| :------------------------------ | :------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------- |
| 履歴リングバッファ（FR-02-2）   | 最古のデータを上書きする（リングラップ）                            | 固定長の移動窓を維持する正常動作であり、エラーではない。                                                   |
| イベントマージキュー（FR-02-1） | 初期化時にエラー（`ERR_CAPACITY_EXCEEDED`）。ホットパスでは溢れない | 各ストリームの先頭1イベントだけをヒープに保持する K-way マージ構造とし、容量を登録ストリーム数で固定する。 |
| アクションキュー（FR-04-1）     | 即座にエラーコード（`ERR_QUEUE_FULL`）を返す。`Poisoned` にはしない | カーネル状態は変更しない。発注の見送りまたは中断は戦略側が判断する。                                       |

## 3. 機能要件（Functional Requirements）

### FR-01: 時間管理および因果律保証

- **FR-01-1（仮想クロック制御）:** システムクロック（OS時刻）の取得を禁止し、カーネルが管理するナノ秒精度の論理タイムスタンプ（`int64` Unix Epoch Nanos）のみを現在時刻として扱うこと。
- **FR-01-2（時刻単調増加の検証）:** 入力イベントのタイムスタンプ $t_{next}$ が現在時刻 $t_{curr}$ 未満（$t_{next} \lt t_{curr}$）である場合、そのイベントを処理せず、`ERR_CAUSALITY_VIOLATION` を返して即時停止（Fail-Fast）すること。カーネルのハンドルは `Poisoned` 状態に遷移する（2.2節）。イベントを暗黙にスキップ（隔離）しない。データ欠損や時刻逆転に気づかないまま結果が歪むことを防ぐためである。
- **FR-01-3（同一時刻イベントの決定論的順序付け）:** タイムスタンプが完全に一致する複数イベントが発生した場合、`StreamID` および入力時の連番（`SequenceID`）の昇順によって処理順序を一意に決定すること。

### FR-02: マルチストリームイベント供給

- **FR-02-1（複数データソースの時刻同期マージ）:** 価格ティック、板情報、指標データ、タイマーイベントなど粒度の異なる複数の `EventFeedPort` を接続し、最小ヒープ（Priority Queue）を用いて時系列順に単一ストリームへ統合配送できること。
- **FR-02-2（視界制限付き履歴ウィンドウ）:** 戦略ロジックへ公開する過去データは、現在時刻 $t_{curr}$ 以下の確定済みイベントのみを格納した固定長リングバッファ経由で提供すること。未確定の未来バッファへのポインタ公開を禁止する。

### FR-03: 状態管理およびスナップショット制御

- **FR-03-1（状態外部化の強制）:** 戦略ロジックが持つ内部状態（インジケータの計算中間値、ポジション状態、未約定注文など）を、カーネル管理下の連続メモリ領域（State Arena）に集約できること。戦略用の固定長領域（`StrategyArena`）は、カーネル初期化時に確保する。Python戦略には、コールバックごとに、書き込み可能なゼロコピービュー（`memoryview` / NumPy配列）として貸与し、コールバックの終了時に無効化する。分岐リプレイやチェックポイント復元を使うPython戦略は、状態変数をこの領域内に置く。
- **FR-03-2（チェックポイント保存と分岐リプレイ）:** 任意のタイムスタンプまたはイベント数間隔で、カーネルおよび戦略の全状態をバイト列としてスナップショット保存できること。後からその時点に復元し、異なるパラメータで分岐リプレイを実行できること。スナップショットの保証対象は State Arena（`StrategyArena` を含む）に限る。Pythonヒープ上の任意のオブジェクト（クラス属性、辞書、クロージャ変数など）は保存対象外とし、その整合性と決定論性はPython戦略の実装側の責任とする。外部ポート（`EventFeedPort` の読み取り位置、`ExecutionPort` の内部状態）も、位置と状態を取得して復元できる契約を持ち、スナップショットに含めること。位置を戻せないデータ源は、`capture` を拒否する。

### FR-04: アクション実行および遅延シミュレーション

- **FR-04-1（非同期アクションキュー）:** 戦略が発行したアクション（注文・状態変更リクエスト）は即座に完了させない。指定されたレイテンシ（処理遅延・通信遅延）を加算した未来のタイムスタンプを持つ「システムイベント」としてイベントキューへ再投入すること。
- **FR-04-2（プラガブルな約定・遷移モデル）:** `ExecutionPort` の実装を差し替えることで、理想約定、スプレッド変動、スリッページ、部分約定などのシミュレーションルールをコアロジック無改修で切り替えられること。約定価格は、約定判定時刻以前に確定した市場データだけから決める。アクションの提出時点では、約定価格を確定しない。

### FR-05: 決定論的乱数生成（Deterministic PRNG）

- **FR-05-1（シード固定と状態保存）:** スリッページや確率的イベントの生成にはOSの乱数デバイスを使用しない。カーネルが保持する決定論的擬似乱数生成器（Xoshiro256 または PCG64）を使用し、その内部状態もスナップショット対象に含めること。

### FR-06: ホスト言語（Python）連携インターフェース

- **FR-06-1（イベント駆動コールバックとバッチ制御）:** Python側で定義した戦略関数をコールバックとして登録できること。Rustで完結するネイティブ戦略モジュールと同一のインターフェースで切り替え可能にすること。
- **FR-06-2（シミュレーション結果のゼロコピー出力）:** リプレイ完了後の約定履歴、資産推移、状態遷移ログを、Apache Arrow形式または連続メモリ配列としてPython（Polars / Pandas / NumPy）へコピーレスで受け渡せること。

## 4. 非機能要件（Non-Functional Requirements）

| カテゴリ       | 要件ID | 要件内容・目標基準                                                                                                                                                                                                            |
| :------------- | :----- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 決定論性       | NFR-01 | 同一の入力データセット、同一の初期設定、同一のPRNGシードを与えた場合、実行環境（OS・インスタンス並列数・スレッドスケジューリング・実行タイミング）に関わらず、最終状態および全出力ログのSHA-256ハッシュ値が100%一致すること。 |
| メモリ効率     | NFR-02 | イベントループのホットパス（初期化完了後から終了まで）における動的ヒープ確保回数を **0回** とすること。最大メモリ使用量は起動時の設定パラメータ（リングバッファ長・アリーナサイズ）により上限が確定すること。                 |
| 処理性能       | NFR-03 | ネイティブ戦略実行時において、単一CPUコアあたり **毎秒1,000万イベント以上** のリプレイスループットを達成すること。                                                                                                            |
| 浮動小数点精度 | NFR-04 | 金額・数量・価格などの累積計算には固定小数点数（`int64` スケール値）または厳密な丸めモード制御を適用し、累積誤差による状態分岐を防止すること。                                                                                |
| 監査・検証性   | NFR-05 | 任意のイベント処理ステップにおいて、入力イベントID・現在時刻・状態ハッシュをトレースログとして出力でき、異常発生時のステップ実行による原因特定が可能であること。                                                              |

## 5. コアポート契約およびデータ構造仕様

本章は要件段階の契約概要である。確定した型定義とメソッドシグネチャは、後続のIF/API仕様書およびDD/DSを正本とする。

### 5.1 基本イベント構造（POD / C互換レイアウト）

メモリキャッシュ効率を最大化するため、イベントヘッダはPlain Old Data（POD）として定義する。

```text
EventHeader (32 bytes, 8-byte aligned)
├── timestamp_ns : int64   // 論理発生時刻（ナノ秒）
├── sequence_id  : uint64  // 同一時刻内の決定論的順序ID
├── stream_id    : uint32  // データソース識別子
├── event_type   : uint16  // イベント種別（Tick, Bar, Timer, Fill, OrderAck等）
├── flags        : uint16  // 制御フラグ（SnapshotTrigger, EndOfStream等）
└── payload_idx  : uint64  // SoAペイロード領域へのインデックスオフセット
```

### 5.2 4大ポートのインターフェース契約

| ポート名        | 責務                               | 主な操作メソッド                                            | 制約・不変条件                                                                                                                    |
| :-------------- | :--------------------------------- | :---------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------- |
| `ClockPort`     | 論理時間の提供と進行管理           | `now_ns()`, `advance_to(target_ns)`                         | 戻り値は常に単調非減少（$t_{n+1} \ge t_n$）。外部からの時刻書き換え不可。                                                         |
| `EventFeedPort` | 外部時系列データの供給             | `peek_next_timestamp()`, `pop_next(out_event)`              | `peek` された時刻より前のイベントを後から挿入してはならない。読み取り位置の取得と復元を提供すること（FR-03-2）。                  |
| `ExecutionPort` | 戦略アクションの受付と遅延結果生成 | `submit_action(action, now_ns)`, `poll_results(out_events)` | アクション受付時刻と同一時刻での即時状態確定を禁止し、必ず遅延イベントとして返す。内部状態の取得と復元を提供すること（FR-03-2）。 |
| `SnapshotPort`  | カーネル・戦略状態の永続化と復元   | `capture(state_blob, timestamp_ns)`, `restore(state_blob)`  | 復元後は `ClockPort` と PRNG の状態も保存時点へ完全に巻き戻ること。                                                               |

## 6. 制約事項・禁止ルール（静的解析・レビュー基準）

コアカーネルの実装コード（`core/` 配下）に対して、次の禁止ルールをCIの静的解析およびコードレビュー基準として適用する。

1. **標準システム時刻APIの使用禁止:** `std::time::SystemTime` と `std::time::Instant` のインポートおよび呼び出しを禁止する。
2. **順序非保証コンテナの使用禁止:** 走査順序がハッシュシードに依存する `std::collections::HashMap` / `HashSet`（既定のランダムシード `RandomState`）の使用を禁止する。配列インデックスアクセス、フラットマップ、または `BTreeMap` などの順序付きツリーを使用する。
3. **ホットパスでのパニック禁止:** イベント処理ループ内で `unwrap()`、`expect()`、配列の範囲外アクセスなどによるパニックを禁止する。エラーコードまたは `Result` 型による明示的な状態遷移を行う。

## 7. 受け入れ条件（Acceptance Criteria）

特に断りがない限り、検証対象はネイティブ戦略である。Python戦略は、GIL とPythonのメモリ確保を含むため、AC-04 と AC-05 の対象外とする。

| AC-ID | 関連要件                | 合格基準（検証方法）                                                                                                                                                                                       |
| :---- | :---------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 | FR-01                   | タイムスタンプが逆行するイベントを入力した際、そのイベントを処理せず `ERR_CAUSALITY_VIOLATION` を返して停止し、ハンドルが `Poisoned` に遷移すること。                                                      |
| AC-02 | FR-01-3 / FR-02 / FR-04 | 複数ストリームの同時刻イベントが常に `(timestamp_ns, stream_id, sequence_id)` の昇順で配送されること。`submit_action` で発行したアクションが、指定レイテンシを加算した時刻より前に約定しないこと。         |
| AC-03 | FR-03                   | 任意時点で `SnapshotPort.capture` を実行後、パラメータを変更して分岐リプレイし、再度 `restore` して同一条件で再実行した結果が、元の実行結果とビット単位で一致すること。対象は State Arena 内の状態に限る。 |
| AC-04 | NFR-01 / NFR-05         | 同一入力・同一シードで単一実行した場合と、16並列インスタンスで同時実行した場合の全出力ログの SHA-256 ハッシュが100%一致すること。                                                                          |
| AC-05 | NFR-02                  | カウンタ付きアロケータを用いたテストで、初期化完了後からループ終了までのヒープ確保・解放回数が0回であること。                                                                                              |
| AC-06 | NFR-03                  | 8章の標準測定条件で、ネイティブ戦略のリプレイスループットが毎秒1,000万イベント以上であること。                                                                                                             |
| AC-07 | NFR-01                  | CIの複数OS（Windows と Linux）で同一入力・同一シードの出力ログの SHA-256 ハッシュが一致すること。                                                                                                          |
| AC-08 | 2.2節                   | アクションキューが満杯のとき `submit_action` が `ERR_QUEUE_FULL` を返し、カーネル状態（状態ハッシュ）が変化せず、ハンドルが `Poisoned` にならないこと。                                                    |

## 8. NFR-03（処理性能）の標準測定条件

- **ハードウェア:** x86_64 のデスクトップCPU。単一物理コアに固定する。基準機の型番は OPEN-06 で確定し、結果報告書に記録する。
- **ビルド:** `--release`、LTO 有効。
- **入力データ:** 2ストリームを統合した計1,000万イベント。1イベントは `EventHeader`（32バイト）とペイロード64バイトの SoA 構成で、合計約1GBになる。入力はあらかじめメモリ上に展開し、ファイルI/Oを計測に含めない。
- **戦略ロジック:** 移動平均の更新、閾値判定、100イベントに1回のアクション発行、10,000イベントに1回の状態ハッシュ計算を含む標準ベンチマーク戦略を使う。FFIコールバックを使わないネイティブRust戦略とする。
