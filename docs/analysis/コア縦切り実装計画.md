# コア縦切り実装計画

設計（要件定義書、BD、DS、DD）を、実測で確かめながら実装へ進めるための計画である。判断の記録であり、仕様の正本ではない。仕様は DD、DS、ENV を正本とする。

## 1. 決定事項

| # | 決定 | 理由 |
| :-- | :-- | :-- |
| 1 | 最初の実装は、`core` の縦切りに絞る（2章） | 性能の前提（H1）と DD の実装可能性（H4）を、早く確かめるため |
| 2 | 実証的に進める。仮説と判定基準を、実装の前に固定する（3章） | 設計だけのレビューでは、`forbid(unsafe_code)` での性能を判断できないため |
| 3 | 実測は、社内の Linux 計算機（4章）で行う。Windows の開発機には、Rust を導入しない | この Windows 機には導入しない方針のため。Linux 側にはすでに Rust がある |
| 4 | Rust は、その計算機のシステムの Rust 1.97.1 を、そのまま使う。`rustup` は導入しない | 追加の導入なしで、すぐに実測を始められるため |
| 5 | Windows と Linux の両方の検証（AC-07）と、Miri（QG-009）は、CI（`ci-rust.yml`）で行う | 計算機は Linux だけで、nightly を使えないため |

## 2. 縦切りの範囲

- **含めるもの**:
  - Cargo ワークスペースの骨組みと `core` クレート（`no_std`、`forbid(unsafe_code)`）
  - `EventHeader`、`KernelConfig`、`create`
  - マージキュー（外部フィード1本とアクションキュー）
  - `step` と `run`（模擬の `EventFeedPort`、`ExecutionPort`、戦略をテスト内に置く）
  - 因果律と連番の検証、同一時刻の順序（`(timestamp_ns, stream_id, sequence_id)`）
  - AC-01、AC-02、AC-05 のテスト
  - `step` のスループットを測るベンチマークの雛形
- **含めないもの**: スナップショットと `restore`、PRNG、状態ハッシュとトレース、Python 境界、`adapters/`。

## 3. 実証する仮説と判定基準

| ID | 仮説 | 実測の方法 | 判定基準 |
| :-- | :-- | :-- | :-- |
| H1 | `forbid(unsafe_code)` と境界検査のままで、NFR-03 を満たせる | 縦切りの `step` ループのベンチマーク（要件定義書 8章に近い入力）。1つの vCPU に固定し、3回以上の中央値を取る | 毎秒1,000万イベント以上。**満たした場合**は、4章の環境（モバイル CPU の仮想機）で達成したので、デスクトップ CPU でも達成できるとみなし、H1 を満たしたと判定する。**満たさない場合**は判定を保留し、ボトルネックの測定結果を記録して、より速い環境で再測定する |
| H2 | `create` の後に、ヒープの確保が起きない | カウンタ付きアロケータのテスト（AC-05） | 確保・解放が0回 |
| H3 | 同じ入力から、同じ出力が得られる | 出力のハッシュの比較。Linux はこの計算機と CI、Windows は CI（AC-04、AC-07） | 完全一致 |
| H4 | DD の手順表は、実装できる粒度である | 手順表に沿って実装し、DD の不足と矛盾を数える | 見つかった不足を、DD の改訂として記録する |

## 4. 実測環境

| 項目 | 内容 |
| :-- | :-- |
| 種類 | 社内の Linux 計算機（KVM 上の完全仮想化。RHEL 8 系） |
| CPU | Intel Core i5-1235U（第12世代のモバイル向け）。vCPU は2（1コアあたり1スレッド）。表示の周波数は 2,496 MHz。公称値で、実際の動作周波数と、P コアか E コアかは、ゲストから確認できない |
| 命令セット | `sse4_2` まで。`avx`、`avx2`、`popcnt` は表示されない（ハイパーバイザが隠している可能性がある） |
| Rust | `rustc` と `cargo` が 1.97.1（Red Hat のパッケージ。2026-07-14）。`rustup` なし |
| 接続 | プロキシ経由で、`static.rust-lang.org` と `index.crates.io` への接続（CONNECT）が成功した。`cargo` での取得は、未確認 |

- この環境は、要件定義書 8章の「デスクトップ CPU」の基準機（OPEN-06）の条件を満たさない。**参考の基準機**として記録する。正式な基準機は、別途決める。
- 測定結果には、`lscpu` の出力と、`rustc -vV` の出力を添える。Red Hat のパッケージは、公式のバイナリとビルド設定が違う可能性があるため、そのことも記録する。

## 5. 未確認事項（実装セッションの最初に確認する）

| 項目 | 確認方法 | 結果の扱い |
| :-- | :-- | :-- |
| `clippy` と `rustfmt` の有無 | `cargo clippy --version`、`cargo fmt --version` | 無い場合、QG-001 と QG-002 は CI だけで実行する |
| `cargo` のプロキシ越しの取得 | 小さなクレートの取得（`cargo fetch`） | 失敗する場合、`~/.cargo/config.toml` のプロキシ設定を、利用者に確認する |
| OS のバージョン | `/etc/os-release` | 測定結果に記録する |
| `perf` の有無 | `perf --version` | 無ければ、ボトルネックの調査は、計測コードを足して行う |

## 6. 実装セッションの手順

1. その Linux 計算機で、このリポジトリの `develop` を開き、Kiro のセッションを新しく始める。
2. 最初に、「`docs/analysis/コア縦切り実装計画.md` に従って、`core` の縦切りを実装する」と伝える。
3. セッションでは、まず 5章の未確認事項を確認する。
4. その後、`feat/core-vertical-slice` ブランチで、DD の手順表に沿って、テストを先に書く TDD で進める。
5. 測定結果と、DD の不足は、そのつど本書か DD に記録する。

## 7. 実装結果（縦切り）

### 7.1 未確認事項の確認結果（5章）

| 項目 | 結果 | 扱い |
| :-- | :-- | :-- |
| `clippy` と `rustfmt` | どちらもない（`cargo clippy`、`cargo fmt` は `no such command`） | QG-001 と QG-002 は、CI だけで実行する。この計算機では、整形と lint を確認していない |
| `cargo` のプロキシ越しの取得 | 成功した（`cargo fetch` で `itoa` 1.0.19 を取得）。`http_proxy` と `https_proxy` は設定済みで、`~/.cargo/config.toml` はない | 追加の設定は要らない |
| OS のバージョン | Rocky Linux 8.10（Green Obsidian） | 測定結果に記録する |

| `rustc -vV` | `rustc 1.97.1 (8bab26f4f 2026-07-14) (Red Hat 1.97.1-1.module+el8.10.0+40435+578e3e63)`、LLVM 22.1.8、host `x86_64-unknown-linux-gnu` | Red Hat のパッケージで、公式のバイナリとビルド設定が違う可能性がある |
| `lscpu` | 4章のとおり（i5-1235U、vCPU 2、KVM の完全仮想化、命令セットは `sse4_2` まで） | 参考の基準機として記録する |

### 7.2 仮説の判定

| ID | 結果 | 判定 |
| :-- | :-- | :-- |
| H1 | `taskset -c 1 cargo bench -p event-kernel-core --bench step_throughput`（`--release`、LTO 有効）。入力は市場イベント1,000万件（ヘッダ32バイトとペイロード64バイトの SoA をメモリ上に展開）。処理件数は 10,199,999（市場1,000万、到達10万、約定99,999）。5回の中央値は **55,340,313 events/s**（範囲は 54,432,940〜56,358,888） | 判定基準（毎秒1,000万以上）を満たした。ただし、縦切りの範囲外の処理（10,000イベントに1回の状態ハッシュ、トレース、2本以上のフィードのマージ）を含まない。これらを実装した後に、再測定する |
| H2 | AC-05 のテスト（`core/tests/alloc_free.rs`）で、`create` の後の `step` と `run` の間の確保と解放が0回 | 満たした（この計算機。CI は未実行） |
| H3 | 状態ハッシュとトレースが範囲外のため、測定していない | 未判定 |
| H4 | 7.3節の不足が見つかった | DD の次の版で反映する |

### 7.3 DD の不足と矛盾（H4）

| # | 内容 | 縦切りでの扱い |
| :-- | :-- | :-- |
| 1 | パッケージ名を `core` にすると、Rust 組み込みの `core` クレートと衝突する | パッケージ名を `event-kernel-core`、ライブラリ名を `ek_core` とした。ディレクトリは `core/` のまま |
| 2 | 外部フィードが返したイベントの、`peek_next_timestamp` との時刻の不一致、登録順と違う `stream_id`、市場イベント（1〜15）以外の `event_type` の扱いがない | `ERR_PORT_FAILURE` とし、`create` ではハンドルを作らず、`step` では `Poisoned` にした |
| 3 | `poll_results` の受け渡しの形がない（「生成した順に返す」だけ） | 確保しないため、1件ずつ `core` のバッファへ書く `poll_result` にした |
| 4 | `ExecutionPort` の結果のヘッダで、`core` が決める項目が `sequence_id` だけ書かれている | `stream_id` を `0xFFFF_FF00`、`payload_idx` を0に上書きした |
| 5 | `run` で、`SnapshotTrigger` と `max_events` が同じイベントで成立したときの優先順位がない | `RUN_SNAPSHOT_REQUESTED` を優先した |
| 6 | `Action.payload` の長さが `payload_record_size - 8` と違う場合の扱いがない | 短い場合は残りを0で埋め、長い場合は `ERR_INVALID_ARGUMENT` にした |
| 7 | 再入を検出したときの `StepResult` の `processed_event_count` と `now_ns` は、本体を借用できないため返せない | 0を入れた |
| 8 | 手順2で選んだアクションキューの先頭を取り出せない場合（内部の不変条件の破れ）のエラーコードがない | `ERR_PANIC` を使った |
| 9 | QG-002 の `core/clippy.toml` の `disallowed_types` は、パッケージ全体（ベンチマークを含む）に効く。ベンチマークの計測には `Instant` が要る | ベンチマークのファイルだけ `allow` にした。ENV の例外として書くかを決める |
| 10 | PRNG を `ExecutionPort` へ渡す方法（DD 2.7節は「`core` が渡す PRNG を使う」だけで、形がない） | `on_arrival` と `on_market_event` に `&mut Prng` の引数を足した。戦略へは `Context::rng()` で渡す |
| 11 | `init_strategy_arena` を `Finished` で呼んだときの結果（3.2節の状態遷移表に行がない） | 表にない操作として `ERR_INVALID_ARGUMENT` にした。入力が空で、最初のステップで `Finished` になった場合も同じ |
| 12 | `TraceSink` の `TRACE_HEADER` 書き込み契機（DS 3.1節は「作成時に書く」、DD 2.7節は `write(record)` のみ） | `TraceSink` に `write_header(&TraceHeader)` を追加し、`trace_enabled=true` の `create_with_trace` で呼び出すようにした |

### 7.4 縦切りの成果物と残件

- **成果物**: Cargo ワークスペース（`Cargo.toml`、`Cargo.lock`、`rust-toolchain.toml`）と、`core/`（`#![no_std]`、`#![forbid(unsafe_code)]`、`clippy.toml`）。テストは `core/tests/` に置き、TR-001〜TR-007、TR-009、TR-014〜TR-022（一部はスナップショット連携後に拡張）の範囲を確かめる。AC-01 は `causality.rs`、AC-02 は `ordering.rs`、AC-04（単一 vs 16並列）は `determinism.rs`、AC-05 は `alloc_free.rs` である。ベンチマークは `core/benches/step_throughput.rs`。
- **残件**: スナップショット（`capture`、`restore`、AC-03）、複数の外部フィード、複数フィード込みの H1 再測定、OPEN-06 正式基準機での再測定。QG-007〜QG-009、QG-012、QG-013 は、対応する機能の PR で追加する。`ci-rust.yml` と QG-003 の検査スクリプトは PR #7 で追加した。
- **テストの進め方**: 手順表に沿って、テストと実装を同じ変更単位で書いた。テストを先に失敗させる手順（red）は、記録していない。
### 7.5 縦切りの後の追加

PR #7 のマージの後に、仕様が決まっていて判断が要らない3つを、別の PR で追加した。

- **PRNG**（DD 2.6節）: Xoshiro256++。シードは SplitMix64 で展開する。SplitMix64 の参照値（seed 0）と、xoshiro256++ の参照列（状態 `[1, 2, 3, 4]`）に一致することをテストで確かめた。
- **PRNG の配線**: `ExecutionPort` が先に引き、戦略が後に引く。両者が1つの乱数列を共有する。同じシードからは、同じ乱数が同じ順に配られる（TR-017 の一部）。スナップショットへの保存は、`capture` と `restore` の実装後に行う。
- **戦略領域の API**（F-011、F-012）: `init_strategy_arena` は `Ready` で `processed_event_count` が0のときだけ成功する。`read_strategy_arena` は `Ready` と `Finished` で成功し、呼び出し側のバッファへコピーする（TR-022）。
- **確認**: テスト35件が合格。`cargo fmt --check` と `cargo clippy -D warnings` も通った。`step` のスループットは、市場イベント100万件・3回の中央値で 56,984,932 events/s だった。入力の件数が7.2節（1,000万件）と違うので、直接は比較しない。
- **未実施**: 状態ハッシュとトレース（OPEN-05 の XXH3-64 の確定が要る）、スナップショット、複数の外部フィード。

### 7.6 状態ハッシュ・トレース・決定論性検証（OPEN-05 / H3 / QG-006 / H1 再測定）

PR #8 のマージ後に、手順9（状態ハッシュ・トレース）と正準バイト列・`state_digest` を実装し、H3・QG-006・H1 再測定を実施した。

- **アルゴリズム確定（OPEN-05）**: 外部クレートを追加せず、純 Rust（`#![no_std]`、`#![forbid(unsafe_code)]`）で XXH3-64（シード0、既定シークレット）と SHA-256 を実装し、xxHash / SHA-256 参照ベクタ 22 件（0〜4,096 バイト）と完全一致することを確認した（`core/tests/hash.rs`）。
- **正準バイト列・トレース出力（EK-DS-001 2.2/2.3/2.5節、EK-DD-001 手順9）**:
  - `TraceHeader`（32バイト、`EKTR`、`hash_algorithm = 1`）・`TraceRecord`（40バイト）・`TraceSink`・`Kernel::create_with_trace`・`Kernel::state_digest` を追加。
  - `hash_interval` ごとに、セクション `2, 3, 4, 5, 6, 8, 9`（`CONFIG` と `HISTORY_RING` を除く）の正準バイト列へ XXH3-64 を適用し、`TR-021`（正準バイト列からのハッシュ値と `TRACE_RECORD.state_hash` の一致、違反ステップでトレース非出力）を確認した（`core/tests/determinism.rs`）。
  - `EventFeedPort::position`（`seekable=false` 時は `token_len=0`）および `ExecutionPort::capture_state` を統合し、`state_digest()` が全9セクションの SHA-256 を返すことを確認した。
- **H2（ゼロアロケーション）**: `trace_enabled=true`・`hash_interval=10` の実行および `state_digest()` 呼び出しで、確保・解放が 0 回であることを確認した（`core/tests/alloc_free.rs`）。
- **H3 / QG-006（決定論性）**: 単一実行と 16 並列スレッド実行（500 市場イベント、`hash_interval=10`、PRNG・`StrategyArena`・`FEED_STATES`・`EXEC_STATE` 込み）で、`state_digest()`・トレースログ全体の SHA-256・`StrategyArena` が全17実行で完全一致することを確認した（`core/tests/determinism.rs`）。Linux と Windows の OS 間一致（AC-07）は `ci-rust.yml` のマトリクスで検証する。
- **H1 再測定（Apple M3 / macOS / Rust 1.99.0、1,000万市場イベント・処理計 10,199,999 件・5回中央値）**:
  - `baseline`（トレース・ハッシュなし）: **69,334,175 events/s**（範囲 66,626,216〜69,498,477）
  - `trace+xxh3(10k)`（`trace_enabled=true`, `hash_interval=10,000`, インメモリ `CountingTraceSink`）: **66,727,682 events/s**（範囲 60,552,566〜68,154,002）
  - オーバーヘッドは約 3.8% に収まり、NFR-03（毎秒 1,000万イベント以上）を満たした（複数外部フィードのマージと正式基準機 `OPEN-06` での測定は別途実施する）。
- **確認**: テスト 42 件が全合格、`cargo fmt --check`・`cargo clippy -D warnings`・`QG-003` も通過した。
- **未実施**: スナップショット（`capture` / `restore`、AC-03）、複数外部フィード（K-way マージ）、Python 境界スパイク（V-01〜V-06）。
