# コア縦切り実装計画

設計（要件定義書、BD、DS、DD）を、実測で確かめながら実装へ進めるための計画である。判断の記録であり、仕様の正本ではない。仕様は DD、DS、ENV を正本とする。

## 1. 決定事項

| # | 決定 | 理由 |
| :-- | :-- | :-- |
| 1 | 最初の実装は、`core` の縦切りに絞る（2章） | 性能の前提（H1）と DD の実装可能性（H4）を、早く確かめるため |
| 2 | 実証的に進める。仮説と判定基準を、実装の前に固定する（3章） | 設計だけのレビューでは、`forbid(unsafe_code)` での性能を判断できないため |
| 3 | 実測は、社内の Linux 計算機（4章）で行う。Windows の開発機には、Rust を導入しない | この Windows 機には導入しない方針のため。Linux 側にはすでに Rust がある |
| 4 | Rust は、その計算機のシステムの Rust 1.97.1 を、そのまま使う。`rustup` は導入しない | 追加の導入なしで、すぐに実測を始められるため |
| 5 | Windows と Linux の両方の検証（AC-07）と、Miri（QG-009）は、CI（`ci-rust.yml`）で行う | 計算機は Linux だけで、nightly を使えないため |

## 2. 縦切りの範囲

- **含めるもの**:
  - Cargo ワークスペースの骨組みと `core` クレート（`no_std`、`forbid(unsafe_code)`）
  - `EventHeader`、`KernelConfig`、`create`
  - マージキュー（外部フィード1本とアクションキュー）
  - `step` と `run`（模擬の `EventFeedPort`、`ExecutionPort`、戦略をテスト内に置く）
  - 因果律と連番の検証、同一時刻の順序（`(timestamp_ns, stream_id, sequence_id)`）
  - AC-01、AC-02、AC-05 のテスト
  - `step` のスループットを測るベンチマークの雛形
- **含めないもの**: スナップショットと `restore`、PRNG、状態ハッシュとトレース、Python 境界、`adapters/`。

## 3. 実証する仮説と判定基準

| ID | 仮説 | 実測の方法 | 判定基準 |
| :-- | :-- | :-- | :-- |
| H1 | `forbid(unsafe_code)` と境界検査のままで、NFR-03 を満たせる | 縦切りの `step` ループのベンチマーク（要件定義書 8章に近い入力）。1つの vCPU に固定し、3回以上の中央値を取る | 毎秒1,000万イベント以上。**満たした場合**は、4章の環境（モバイル CPU の仮想機）で達成したので、デスクトップ CPU でも達成できるとみなし、H1 を満たしたと判定する。**満たさない場合**は判定を保留し、ボトルネックの測定結果を記録して、より速い環境で再測定する |
| H2 | `create` の後に、ヒープの確保が起きない | カウンタ付きアロケータのテスト（AC-05） | 確保・解放が0回 |
| H3 | 同じ入力から、同じ出力が得られる | 出力のハッシュの比較。Linux はこの計算機と CI、Windows は CI（AC-04、AC-07） | 完全一致 |
| H4 | DD の手順表は、実装できる粒度である | 手順表に沿って実装し、DD の不足と矛盾を数える | 見つかった不足を、DD の改訂として記録する |

## 4. 実測環境

| 項目 | 内容 |
| :-- | :-- |
| 種類 | 社内の Linux 計算機（KVM 上の完全仮想化。RHEL 8 系） |
| CPU | Intel Core i5-1235U（第12世代のモバイル向け）。vCPU は2（1コアあたり1スレッド）。表示の周波数は 2,496 MHz。公称値で、実際の動作周波数と、P コアか E コアかは、ゲストから確認できない |
| 命令セット | `sse4_2` まで。`avx`、`avx2`、`popcnt` は表示されない（ハイパーバイザが隠している可能性がある） |
| Rust | `rustc` と `cargo` が 1.97.1（Red Hat のパッケージ。2026-07-14）。`rustup` なし |
| 接続 | プロキシ経由で、`static.rust-lang.org` と `index.crates.io` への接続（CONNECT）が成功した。`cargo` での取得は、未確認 |

- この環境は、要件定義書 8章の「デスクトップ CPU」の基準機（OPEN-06）の条件を満たさない。**参考の基準機**として記録する。正式な基準機は、別途決める。
- 測定結果には、`lscpu` の出力と、`rustc -vV` の出力を添える。Red Hat のパッケージは、公式のバイナリとビルド設定が違う可能性があるため、そのことも記録する。

## 5. 未確認事項（実装セッションの最初に確認する）

| 項目 | 確認方法 | 結果の扱い |
| :-- | :-- | :-- |
| `clippy` と `rustfmt` の有無 | `cargo clippy --version`、`cargo fmt --version` | 無い場合、QG-001 と QG-002 は CI だけで実行する |
| `cargo` のプロキシ越しの取得 | 小さなクレートの取得（`cargo fetch`） | 失敗する場合、`~/.cargo/config.toml` のプロキシ設定を、利用者に確認する |
| OS のバージョン | `/etc/os-release` | 測定結果に記録する |
| `perf` の有無 | `perf --version` | 無ければ、ボトルネックの調査は、計測コードを足して行う |

## 6. 実装セッションの手順

1. その Linux 計算機で、このリポジトリの `develop` を開き、Kiro のセッションを新しく始める。
2. 最初に、「`docs/analysis/コア縦切り実装計画.md` に従って、`core` の縦切りを実装する」と伝える。
3. セッションでは、まず 5章の未確認事項を確認する。
4. その後、`feat/core-vertical-slice` ブランチで、DD の手順表に沿って、テストを先に書く TDD で進める。
5. 測定結果と、DD の不足は、そのつど本書か DD に記録する。
