# ADR-003: Python FFI境界方式の選定

- **ステータス**: Proposed（ドラフト。未承認）
- **作成日**: 2026-11-24
- **決定対象**: RustコアカーネルとPythonホスト層の間のFFI境界方式（要件定義書 OPEN-02）
- **関連Issue**: なし

## 1. 背景

要件定義書は次の制約を置いている。

- コアカーネルは外部I/Oとホスト言語のランタイムから隔離する（2章）。
- コアとPythonの境界は C ABI で固定し、FFIコール回数を最小化する（2.1節）。
- Python側の戦略関数をコールバックとして登録でき、Rustのネイティブ戦略と同一インターフェースで切り替えられる（FR-06-1）。
- 結果は Apache Arrow 形式または連続メモリ配列で、コピーなしにPython（Polars / Pandas / NumPy）へ渡す（FR-06-2）。
- ホットパスでヒープ確保0回（NFR-02）、同一入力で出力のSHA-256が一致（NFR-01）。
- ネイティブ戦略で毎秒1,000万イベント以上（NFR-03）。性能目標はネイティブ戦略のみが対象で、Python戦略の目標値は未定義。

プロジェクトの `requires-python` は `>=3.10`、開発用の `.python-version` は `3.12` である。

## 2. 評価基準

| ID   | 基準                                         | 関連要件      |
| :--- | :------------------------------------------- | :------------ |
| C1   | コアがPythonランタイムに依存しない（隔離性） | 2章           |
| C2   | Pythonコールバックを登録できる               | FR-06-1       |
| C3   | 結果をコピーなしで渡せる                     | FR-06-2       |
| C4   | 境界通過回数を減らせる（バッチ化）           | 2.1節、NFR-03 |
| C5   | 決定論性を壊しにくい（GIL、パニック、再入）  | NFR-01        |
| C6   | 配布・ビルドの容易さ                         | 運用          |
| C7   | 将来の本番アダプタ・他言語ホストへの拡張性   | 1.2節         |

## 3. 選択肢

### 案A: C ABI（`extern "C"` と `cbindgen`）のみ。Python側は `ctypes` または `cffi`

コアが `#[repr(C)]` の型と `extern "C"` 関数を公開し、`cbindgen` でCヘッダを生成する。Python側が `ctypes` / `cffi` で呼び出す。

- 利点: コアがPythonに依存しない（C1）。他言語ホストにも同じ境界を使える（C7）。Pythonのバージョンに依存しない共有ライブラリになる。
- 欠点: Pythonコールバックは `ctypes.CFUNCTYPE` などの関数ポインタ経由になり、呼び出しごとにGILの取得が必要になる（C2、C4）。Arrow は C Data Interface の構造体を自前で組み立てる必要がある（C3）。ライフタイム管理とエラー変換をすべて手書きする。Pythonパッケージのビルドと配布は別途整備が必要（C6）。

### 案B: PyO3 と `maturin` のみ（コア crate が PyO3 に直接依存）

コア crate 自体を Python 拡張モジュールとして公開する。

- 利点: コールバック、例外変換、バッファプロトコル、Arrow PyCapsule の実装が容易（C2、C3）。`maturin` でwheelを作れる（C6）。
- 欠点: コアが PyO3 とPythonに依存し、要件の「ホスト言語ランタイムから完全に隔離」に反する（C1）。コアのビルドとテストにPythonが必要になる。C ABI が要件にあるため、後から別途用意することになり二重管理になりうる（C7）。

### 案C: 層分離（推奨）。コアは純Rust＋C ABI層、PyO3 は別 crate のバインディング

3つの crate に分ける。

1. `core`: 純Rust。PyO3 に依存しない。イベントループ、ポート、PRNG、スナップショット。
2. `core-capi`: `core` を C ABI で公開する薄い層。`cbindgen` でヘッダを生成する。`#[repr(C)]` の `EventHeader` などの境界型を定義する。
3. `bindings/python`: PyO3 と `maturin` によるPython拡張。`core` の型を直接使い、Pythonコールバック、NumPy / Arrow の受け渡しを実装する。

- 利点: コアはPythonから隔離される（C1）。Pythonバインディングでは PyO3 の機能を使える（C2、C3）。C ABI層が他言語ホストと将来の本番アダプタの契約になる（C7）。
- 欠点: crate が3つになり、`core-capi` と `bindings/python` の2つの公開面を保守する。2つの面で挙動がずれないよう、共通の契約テストが必要になる。

### 案D: 共有メモリ（プロセス間）またはサブプロセス＋Arrow IPC

コアを別プロセスで動かし、共有メモリまたは Arrow IPC でデータを交換する。

- 利点: Pythonとの完全な隔離（C1）、クラッシュの分離。
- 欠点: Pythonコールバックがプロセスをまたぐと、イベントごとの往復遅延が大きい（C2、C4）。同期プロトコルが複雑になり、決定論性の検証対象が増える（C5）。要件の「C ABI / ゼロコピーFFI」から外れる。

## 5. 決定（推奨案）

**案C（層分離）を推奨する。** 要件の隔離性（C1）と、Pythonコールバックおよびゼロコピー出力（C2、C3）を同時に満たせるのは案Cだけである。案Aは C2 と C3 の実装コストが高く、案Bは C1 に反する。

以下の設計方針を、案Cの採用条件とする。

### 5.1 境界の設計方針

1. **境界型は `#[repr(C)]` の固定レイアウトにする。** `EventHeader` は32バイトで、`const` のサイズ・オフセット検査をコンパイル時に行う。
2. **コールバックはバッチ単位を基本にする。** イベントごとのPython呼び出しは、境界通過コストとGIL取得が支配的になる。同一時刻または一定件数のイベントを連続メモリのビューにまとめて渡す方式を標準とし、イベント単位は互換用に残す。
3. **コールバック中のカーネルへの再入を禁止する。** Python戦略に渡すコンテキストは読み取り専用（FR-02-2）とし、アクションは `ExecutionPort` への `submit_action` のみとする。再入が検出された場合はエラーコードを返す。
4. **パニックを境界で止める。** `std` を使える `core-capi` の全 `extern "C"` 関数は、`std::panic::catch_unwind(AssertUnwindSafe(...))` で本体を囲み、パニックをエラーコード（例: `ERR_PANIC = -99`）に変換する。Rust 1.81 以降は `extern "C"` 関数からアンウィンドが出ると異常終了するため、この捕捉は必須である。`bindings/python` では PyO3 が入口でパニックを `PanicException` に変換する。`core` を `#![no_std]` にする場合、`core` 自身は `catch_unwind` を使えないので、捕捉は `core-capi` と `bindings/python` の入口に置く。`catch_unwind` は `panic = "unwind"` でのみ働く。境界を含むバイナリで `panic = "abort"` を使うことは禁止する（6章）。
5. **結果出力は Arrow PyCapsule インターフェース（`__arrow_c_stream__` など）と、NumPy が読める連続メモリのいずれかで提供する。** PyCapsule は Arrow の公式仕様で、デストラクタで `release` コールバックを呼ぶ。Arrow の仕様は取得時点で v26.0.1。
6. **Pythonコールバック実行中のスレッドとGILの扱いを固定する。** カーネルは単一スレッドで動かし、コールバックは同じスレッドから呼ぶ。コールバックが非決定的な処理（システム時刻、乱数）をしても、カーネルの状態ハッシュ（NFR-05）には含めない。Python戦略の決定論性は、Python戦略側の責任範囲として明記する。

7. **コールバックに渡す入力ビューは、コールバック終了時に必ず無効化する。** 入力バッチはカーネルのリングバッファ上の領域を指す。Python側が `self.last_batch = batch` のように参照を保持すると、次のイベントで領域が上書きされ、ダングリング参照になる。これを防ぐため、ビューは有効期限フラグまたは世代カウンタを持つ。カーネルはコールバックの `return` 直前（例外で抜ける場合も含む）にビューを無効化する。無効化は `Drop` トレイトで有効フラグを倒すスコープガード（`ViewGuard`）で行う。ガードをコールバック呼び出しの前に生成すれば、正常終了、早期リターン、Python例外のいずれの経路でも確実に無効化される。Rust のパニックでアンウィンドする場合も `Drop` は実行されるので、`panic = "unwind"` の前提（5.1-4）と整合する。無効化後にビューへアクセスすると `RuntimeError` を送出する。この規則の対象は入力バッチのビューである。戦略用領域（`StrategyArena`、要件定義書 FR-03-1）のビューは、書き込み可能で、カーネルの寿命と同じ期間有効とし、コールバックごとの無効化の対象にしない。`restore` はこの領域を同じアドレスのまま上書きする。ビューからバッファプロトコルのエクスポート（`memoryview` など）が出ている場合も、無効化の時点でアクセスを拒否する。一方、リプレイ完了後の結果出力（5.1-5）は所有権の移譲で安全にゼロコピーにできる。結果バッファの所有者（`Arc` または `Box`）を Arrow PyCapsule の `private_data` に渡し、`release` コールバックで解放する。
8. **境界の共通ロジックは `core` の安全なRust API に集約する。** バッチ分割、再入ガード（5.1-3）、エラーコードの定義（`#[repr(C)]` の列挙）、ハンドルの状態遷移（5.1-9）は `core` に置く。`core-capi` と `bindings/python` は、この API を C ABI と PyO3 の型へ変換するだけの薄い層とする。これにより、2つの公開面は同じ実装を共有し、V-03（出力SHA-256の一致）の維持コストが下がる。`bindings/python` が `core-capi` を経由する構成は採らない。`core-capi` は生ポインタ中心の層で、PyO3 のオブジェクトと例外変換の利点を失うためである。
9. **パニックを捕捉したとき、および因果律違反（要件定義書 FR-01-2）を検出したとき、カーネルのハンドルを `Poisoned` 状態にする。** `Poisoned` のハンドルに対する `step`、`snapshot`、`submit_action` は、すべて `ERR_POISONED` で拒否する。中途半端な状態から非決定的に続行することを防ぐ。状態は `core` のハンドルが持つので、C ABI とPythonのどちらの入口でパニックが起きても同じ結果になる。`Poisoned` からの `destroy` は許可する。`Poisoned` からの `restore`（保存済みスナップショットへの復旧）を許可するかどうかは DD で決める。判断基準は次のとおり。
    - **許可する条件（すべてを満たすこと）:** `restore` が既存のカーネル状態（State Arena、PRNG、イベントキュー）を一切読まずに、スナップショットのバイト列で全領域を上書き初期化できる。かつ、外部ポート（`EventFeedPort`、`ExecutionPort`）にも状態リセットの契約がある。`Poisoned` の解除は、復元が最後まで成功した時点でのみ行う。復元中に失敗またはパニックした場合は `Poisoned` を維持する。
    - **禁止する条件:** 外部アダプタが、スナップショットに含まれない可変状態（バッファの残存データなど）を持つ。この場合はカーネル単体の復元で整合性を保証できないため、ハンドルを破棄して再生成する。

### 5.2 対象バージョン

- PyO3 は 0.30.0（2026-10-13公開）を基準に評価した。MSRV は Rust 1.85、Python 3.8 のサポートは終了している。本プロジェクトの `requires-python >=3.10` と矛盾しない。
- `abi3`（安定ABI）のwheelを使うかどうかは、性能の測定結果で決める。

## 6. トレードオフ

- 境界を含むバイナリは `panic = "unwind"` を使う。`panic = "abort"` のほうがバイナリは小さくなりうるが、`catch_unwind` が効かなくなるため採用しない。ホットパスでのパニック禁止（要件定義書6章）は、別途 Clippy の lint で守る。
- 公開面が `core-capi` と `bindings/python` の2つになる。共通ロジックは `core` に集約する（5.1-8）が、契約テスト（同じシナリオを両方の境界から実行し、出力のSHA-256を比較する）を品質ゲートに加える必要がある。
- Python戦略のスループットは、NFR-03（ネイティブ戦略で毎秒1,000万イベント）の対象外であり、要件にも目標値がない。バッチ化の効果は実測が必要である。
- `maturin` と `cbindgen` がビルド手順に加わる。詳細は環境・開発基盤仕様書で定義する。

## 7. 検証計画（承認前に実施する項目）

実測値はまだない。次のスパイクで案Cの前提を確認してから承認する。

| ID   | 検証内容                                                                     | 判定基準（案）                                                                         |
| :--- | :--------------------------------------------------------------------------- | :------------------------------------------------------------------------------------- |
| V-01 | Pythonコールバックのイベント単位とバッチ単位のスループット比較               | 結果を記録し、Python戦略の目標値の根拠にする                                           |
| V-02 | Arrow PyCapsule 経由で Polars / PyArrow へ渡す際のコピー有無                 | コピーなし（メモリアドレスの一致またはアロケーション計測）                             |
| V-03 | `core-capi` と `bindings/python` で同一シナリオの出力SHA-256が一致するか     | 完全一致                                                                               |
| V-04 | コールバック内でのパニックとPython例外の境界伝播                             | 境界の外へ伝播せず、エラーコードまたは例外に変換される                                 |
| V-05 | コールバック終了後に保持した入力ビューへアクセスする（例外終了の場合を含む） | `RuntimeError` が送出され、メモリ破壊（Miri または AddressSanitizer で検査）が起きない |
| V-06 | パニック発生後に `step` / `snapshot` を呼ぶ。C ABI とPythonの両方で実施する  | 両方で `ERR_POISONED` 相当の拒否になり、結果が一致する                                 |
